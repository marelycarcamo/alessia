# 05. Despliegue

## Introducción

Una vez finalizado el desarrollo de la primera versión, ALESSIA fue preparada para su ejecución tanto en un entorno local como en la nube.

El objetivo del despliegue fue demostrar que la aplicación podía ejecutarse de forma estable en un entorno accesible para cualquier usuario, manteniendo la misma arquitectura utilizada durante el desarrollo.

---

## Entornos de ejecución

La primera versión de ALESSIA fue diseñada para funcionar en dos escenarios:

### Desarrollo local

El entorno local fue utilizado durante todas las etapas de implementación, pruebas y validación del proyecto.

Este entorno permitió desarrollar los distintos módulos de forma incremental, realizar pruebas unitarias, validar el pipeline RAG y experimentar con distintas configuraciones antes de su publicación.

---

### Despliegue en la nube

Como demostración funcional del proyecto, ALESSIA fue desplegada utilizando **Streamlit Community Cloud**.

Este entorno permitió publicar una versión accesible desde un navegador web, facilitando la evaluación del proyecto sin necesidad de realizar instalaciones locales.

El despliegue en la nube también permitió validar que la arquitectura desarrollada funcionara correctamente fuera del entorno de desarrollo.

---

## Componentes del despliegue

Durante la ejecución, la aplicación integra distintos componentes que trabajan de forma coordinada.

Entre ellos:

* aplicación desarrollada con Streamlit;  
* base vectorial con ChromaDB;  
* modelo de embeddings para recuperación semántica;  
* modelo de reranking para mejorar la relevancia de los resultados;  
* modelo de lenguaje accedido mediante OpenRouter o NVIDIA, según `DEFAULT_PROVIDER`;  
* documentación oficial utilizada como base de conocimiento.

Cada componente mantiene una responsabilidad específica dentro del sistema y contribuye al funcionamiento del pipeline RAG.

Los modelos de embeddings y reranking se descargan la primera vez que se ejecutan: cerca de 900 MB en total con la configuración por defecto. En un entorno de despliegue eso alarga el primer arranque, y si la plataforma no conserva el sistema de archivos entre reinicios, la descarga se repite en cada uno.

---

## Procedencia de los documentos

Las fuentes oficiales están registradas en `data/raw/muni_valdivia/sources.json`: URL de origen, tamaño, `sha256` y fecha de modificación informada por el servidor.

El hash es lo que permite afirmar que el PDF del repositorio **es** el que se indexó. Una URL puede servir contenido distinto mañana sin cambiar de dirección, así que la dirección sola no sirve como prueba.

Dos observaciones que salieron al verificar las fuentes:

* el servidor de la municipalidad **no envía `ETag`**, de modo que detectar cambios requiere comparar tamaño y hash —no existe un identificador de versión que consultar;
* el archivo del plan de inundación ya viene comprimido desde el origen (`_compressed` en el nombre publicado), así que recomprimirlo sería comprimir dos veces.

---

A diferencia de los datos derivados habituales, el índice de `data/vector_store/` **se versiona**.

La razón es concreta: Streamlit Community Cloud no ofrece un paso de compilación donde ejecutar `scripts/build_index.py`. Si el índice no viaja en el repositorio, la aplicación arranca con la colección creada pero vacía, y responde "No encontré información" a cualquier consulta **sin mostrar ningún error**. Es un modo de fallo silencioso: el motor parece funcionar y el problema es que no hay documentos.

### Cuándo hay que reindexar y volver a commitear

Cada vez que cambie cualquiera de estas tres cosas:

* los documentos de `data/raw/`;
* el modelo de embeddings configurado en `EMBEDDING_MODEL`;
* la estrategia de fragmentación en `chunker.py`.

El procedimiento es:

> Antes de ejecutarlo, **cierra la aplicación**. Si está abierta mantiene el archivo de ChromaDB en uso: la reconstrucción no puede borrar el índice anterior y dos procesos terminan escribiendo sobre el mismo store, con conteos inconsistentes.

```bash
python scripts/build_index.py --recreate
python scripts/evaluate_retrieval.py    # confirmar que la recuperación sigue bien
git add data/vector_store
git commit -m "chore(index): reindexa tras <cambio>"
```

Omitir la reindexación al cambiar el modelo de embeddings es especialmente peligroso: si la dimensión de los vectores coincide, la búsqueda no falla, simplemente devuelve fragmentos sin relación con la consulta.

---

## Configuración

ALESSIA fue diseñada para separar el código fuente de la configuración del entorno.

Las variables sensibles, como las credenciales de acceso a servicios externos, no forman parte del repositorio y se gestionan mediante variables de entorno.

Este enfoque permite:

* proteger información sensible;  
* facilitar el despliegue en distintos entornos;  
* mantener una configuración flexible y reutilizable.

---

## Desafíos encontrados

Durante el proceso de despliegue se identificaron diversos desafíos técnicos que requirieron ajustes en la configuración del proyecto.

Entre ellos destacan:

* diferencias entre el entorno local y el entorno de producción;  
* configuración segura de credenciales y variables de entorno;  
* compatibilidad de dependencias durante el despliegue;  
* validación del funcionamiento del pipeline completo en la nube.

La resolución de estos desafíos permitió fortalecer el proceso de despliegue y mejorar la portabilidad de la aplicación.

---

## Validación del despliegue

Una vez publicada la aplicación se verificó el funcionamiento de los principales componentes del sistema.

Las validaciones incluyeron:

* carga correcta de la interfaz;  
* procesamiento de consultas;  
* recuperación de información desde la base vectorial;  
* generación de respuestas utilizando el modelo de lenguaje;  
* funcionamiento del flujo completo desde la consulta hasta la respuesta final.

Estas pruebas confirmaron que la aplicación mantenía el mismo comportamiento observado durante el desarrollo local.

---

## Consideraciones de seguridad

Durante el despliegue se adoptaron medidas para proteger la configuración del proyecto.

Entre ellas:

* exclusión de archivos con credenciales del control de versiones;  
* utilización de variables de entorno para servicios externos;  
* separación entre configuración y código fuente.

Estas prácticas contribuyen a reducir riesgos asociados a la exposición de información sensible y facilitan la publicación del proyecto como software abierto.

---

## Evolución del despliegue

La estrategia de despliegue fue concebida como un punto de partida para futuras versiones del proyecto.

La arquitectura actual permite incorporar mejoras como:

* automatización del proceso de despliegue;  
* integración continua (CI/CD);  
* monitoreo del sistema;  
* registro de eventos y métricas;  
* nuevas alternativas de alojamiento según la evolución del proyecto.

Estas mejoras podrán incorporarse de manera gradual sin requerir cambios estructurales en la arquitectura de ALESSIA.

---

## Consideraciones finales

El despliegue de ALESSIA representó la etapa en la que el proyecto pasó de un entorno de desarrollo a una aplicación funcional accesible para terceros.

Más allá de la publicación de la interfaz, este proceso permitió validar la arquitectura en un entorno real, identificar desafíos propios de la puesta en producción y consolidar prácticas relacionadas con configuración, seguridad y portabilidad.

La experiencia obtenida durante esta etapa constituye una base sólida para futuras versiones del proyecto y para la incorporación de nuevas capacidades orientadas a mejorar la disponibilidad y escalabilidad de la aplicación.
